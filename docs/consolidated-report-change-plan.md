**Item 3: seasonal SLA as several SLA Configuration records per category.**

A category has one default record plus any number of seasonal records. Each seasonal record is a full configuration: `sla_days`, state timers, first response, escalation threshold.

- **Schema.** Add `season_start_month` and `season_end_month` to Grievance SLA Configuration. Both empty means the default, all-year record. A window may wrap the year end (for example Oct–Jan).
- **Region.** Add an optional region (a link to Grievance Administrative Area) to Grievance SLA Configuration, because the seasons differ by region. A record with no region is the fallback for every region. The case's region is the nearest region ancestor of its area, found the way routing walks the area tree.
- **Validation.** Replace `validate_one_active_row` with:
  - exactly one active default record per category and region;
  - active seasonal records of a category and region must not overlap.
- **Resolution.** `resolve_policy` takes the records for the case's region (a record with no region applies everywhere), picks the active seasonal record whose window contains the case's filing date, and otherwise the default. The season is fixed at filing, so a running case does not change timers when the season ends.
- **What a season changes.** Mainly `sla_days`, plus first response and the escalation threshold. State timers (`Resolved` and `More Info Needed` auto-close after 7 days by default) wait on the submitter. Shortening them in season would close cases on farmers sooner, so they normally stay the same as the default record.
- **Readers to update.** These assume one row per category today: `active_sla_rows` and the category assignment API (which show and edit "the" SLA of a category), the state-timer lookup in `services/sla.py` (around line 416, `get_value` by category and active), `api/v1/sla_settings.py`, and the OpenAPI spec.
- **C17.** C17 is urgent all year, so it only needs a short default record.
- **Desk dates.** Desk `effective_from` / `effective_to` stay for desk lifetime. They are one-off dates, not yearly seasons.
- **Calendar.** The report wants windows shown in both calendars (Meher is Jun–Aug, Ginbot–Hamle). Store Gregorian months and show the Ethiopian months in the UI.

**Item 4: Zone and Region levels.** The Regional head is the existing desk head: the top rung (`department_head`), with Region as the area on their officer row. That part is configuration.

Zone is the part that needs a rung. Escalation climbs rungs, not areas (`higher_authority_of`, `services/sla.py:561`):

- It stops when the case is on the top rung.
- `reports_to` is followed only when the supervisor sits on a higher rung.

So with three rungs, Kebele → Woreda → desk head skips Zone, even if a Zone officer is on the desk.

The fix is configuration: insert a Zone rung between `senior_nodal_officer` (20) and `department_head` (30), for example at order 25, with `escalation_hours` set. `department_head` stays the top rung, so `top_rung()` and the department-head checks in `permissions.py` are unchanged. `seed_role_levels` only inserts missing rows, so a migrate won't remove the new rung.

The code change is to stop hard-coding the ladder. Grievance Role Level is the source of truth, but the places below keep their own copy of it. The fix is to derive each from `GrievanceRoleLevel.get_chain()`, not to add a fourth hard-coded entry.

Public labels stay `L1…Ln`, computed from the rung's position in the chain. With a Zone rung at order 25, that gives L1 Kebele, L2 Woreda, L3 Zone, L4 Region. Clients that send `L3` for the desk head today must send `L4`. Accepting `level_code` (`nodal_officer` etc.) directly would avoid the renumbering, but breaks the API contract.

## 2. Configuration only

Where each piece lives, loaded by §1 #21:

- **Role levels, workflow states, default notification templates:** this repo, seeded on install and migrate. The code depends on the rung codes, so an app version ships with the ladder it needs, and seeding only inserts missing rows, so a migrate never removes a rung.
- **Ethiopia reference configuration** (departments, categories, SLA values, pause reasons, holidays): a versioned pack in this repo, for example `setup/packs/ETH/`. It refers to rung codes and template placeholders, so it changes together with the code. Another country adds another pack directory.
- **Administrative areas:** `openg2p-data` `packs/ETH`. That repo holds geography and sample people for OpenG2P, and is not versioned with this app.
- **Dev dummy data:** `setup/demo_data.py` in this repo. A full dev reset is the chart's reset Job (§1 #21).
- **Real desks with named officers:** the admin UI or API, per environment. Real people do not go in any repo.
- **Deployment values** (SMS credentials, hosts): that deployment's chart values and secrets.
