# Ticket Export (SOW Annexure form)

Audience: backend and frontend developers adding the Export button to the case view (STG-469).

One grievance, with its timeline, downloaded as the paper complaint form from the SOW Annexure ("Sample Manual Complaint Process Form"), as a PDF or a CSV. The source document is `EAON_PLAN_SOW_Services_Grievance_D2`.

## 1. Endpoint

`GET /api/v1/grievances/{ticket_number}/export?format=pdf|csv&lang=en|am`

| Part     | Value                                                                                                                                                                                                                                                 |
| :------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Format   | `pdf` (default) or `csv`, any case. Anything else is a `400 VALIDATION_ERROR`                                                                                                                                                                         |
| Language | `en` (default) or `am`, any case: the language of the form's own wording (§7). Anything else is a `400 VALIDATION_ERROR`. An Amharic file is named `grievance-<ticket>-am.<format>`                                                                   |
| Ticket   | As typed: `3-001-002A-0`, `3001002A0` or the lower-case form                                                                                                                                                                                          |
| Success  | The file itself, `Content-Disposition: attachment; filename=grievance-<ticket>.<format>`, `Cache-Control: no-store`                                                                                                                                   |
| Failure  | The usual JSON error envelope: `403 PERMISSION_DENIED` (no export role), `404 NOT_FOUND` (no such ticket, or one the caller may not read), `400 VALIDATION_ERROR` (a bad `format` or `lang`, or a case too large to export, §4), `500 INTERNAL_ERROR` |
| Gateway  | `citizen-intake` tier (60 a minute), which also bounds the cost of rendering a PDF                                                                                                                                                                    |

The CSV is UTF-8 with a byte-order mark, so a spreadsheet reads Amharic. It has one fact per line, in four columns: `Section`, `Entry`, `Field`, `Value`. A key/value row has no `Entry`; a table row is named by its table and position (`Decisions 2`). A cell that a spreadsheet would run as a formula (`=`, `+`, `-`, `@` followed by anything but a number) is prefixed with `'`.

## 2. Who may export, and what the file holds

Two checks, in this order:

1. **Role.** The caller holds the Grievance `export` permission, or the answer is `403 PERMISSION_DENIED`. That is Grievance Admin, System Manager, Grievance Officer, Grievance Submitter and Grievance Assisted Submitter. The Review Officer has none: it is read-only oversight and is left out. The route checks it with `@require_permission("Grievance", "export")`, as the timeline route does for `read`, so the rule is the DocPerm flag and nowhere else. The guard runs before the query is validated, so a caller without the role learns nothing about the request schema, and it answers the same whether or not the ticket exists. It refuses before the export service runs, so a role refusal writes no audit row (§3).
2. **Case.** The caller may read this case (`has_grievance_permission`): their own case or one they assisted, a case assigned to them or their reporting chain, or a case inside their desk scope. If not, the answer is `404 NOT_FOUND` with the same message as a ticket that does not exist. Every submitter holds the export permission, so a different answer here would tell any of them which tickets exist. The audit row says which of the two it was.

The file holds what the caller could already read on the case, no more:

| Content                                            | Staff                            | Submitter                      |
| :------------------------------------------------- | :------------------------------- | :----------------------------- |
| Internal notes, internal timeline entries          | Yes                              | No                             |
| Officer names (assignee, authors, decided by)      | Yes                              | No: "Officer" or "Complainant" |
| Status-history `notes`, notification channels used | Yes                              | No                             |
| Anonymous case: name, phone, email                 | Sealed unless `can_see_identity` | Own case only                  |
| Attachment bytes, file URLs                        | Never                            | Never                          |

Attachments are listed with name, type, size, upload time and scan status, including files that are infected or not yet scanned; nothing is embedded.

## 3. Audit

Every attempt that passes the role check writes one `Grievance Access Audit Event`, committed before the response, because the API error handler rolls the request back and a refusal would otherwise leave nothing behind. A caller without the export permission is stopped by the route guard first and writes no row, as on every route that uses `require_permission`.

A file is returned only after its row is written. The row is written last, once the file exists, and if it cannot be written or committed the export fails with `500` and no file leaves. Nothing is handed over without a record of it.

**Exports at the same time.** Audit rows are named at random (the doctype's `autoname` is `hash`, `naming_rule` `Random`). They used to be numbered from one counter row in `tabSeries` that every audit write moved. A PDF export reads the case, spends a few hundred milliseconds rendering, and only then writes its row, so it holds one database snapshot all that time; on MariaDB 11.6 and later (snapshot isolation is the default) the insert then failed with `Record has changed since last read in table 'tabSeries'` whenever another request audited in between. That is how a PDF export came to fail with `ExportNotRecorded` while a CSV export, which is over in a few milliseconds, almost never did. With no shared counter there is nothing to lose: the same concurrency check that failed 23 of 36 exports before passes 36 of 36 with the old code once the names are random. Two things remain as defence in depth. A durable audit write commits first, which ends the request's stale snapshot and loses nothing (the write commits straight after), and an insert that still loses a race (a lock conflict, or a random name already taken) is rolled back and tried again, up to three times in all. A retry can only follow a failed insert, never a failed commit, so one export never leaves two rows. If every attempt fails the export still ends in `500` with no file, and the cause is in the Error Log under `Access audit write failed`. Rows written by other callers without `durable=True` are unchanged. Existing rows keep their `GR-AUDIT-00000000` names, and nothing sorts or filters on the name: read the trail by `timestamp`. **Deploying this needs `bench migrate`** (or a reload of the doctype) so the site picks up the new naming rule.

| Outcome                                 | `action`        | `decision` | `scope_evaluated`                                                     |
| :-------------------------------------- | :-------------- | :--------- | :-------------------------------------------------------------------- |
| File produced                           | `export`        | `Allowed`  | `format=pdf; lang=en; outcome=success; bytes=31162; sha256=87dc96...` |
| Caller cannot read the case             | `export`        | `Denied`   | `format=pdf; lang=en; reason=case_access`                             |
| No such ticket                          | `export`        | `Denied`   | `format=pdf; lang=en; ticket=<first 40 characters>; reason=not_found` |
| Cleared, but the file could not be made | `export_failed` | `Allowed`  | `format=pdf; lang=en; reason=generation_error (RuntimeError)`         |

The row links the grievance when there is one, and carries the user, their role and the request path. It never carries anything from the complaint. A request with an invalid `format` is rejected before any of this runs and is not an export attempt.

`export` rows mean a file left the system. To list who took one: `action = export` and `decision = Allowed`.

**Matching a file to its export.** A successful row carries the file's size and SHA-256. Given a copy, `sha256sum` it and search `scope_evaluated` for the digest: a match names the user, the time and the case, and a copy that has been edited since matches nothing. The file itself carries no signature or seal (§6).

**Refusal rows are rationed.** A refusal always happens, but one account's refusals write at most 10 rows a minute (`MAX_DENIAL_ROWS_PER_MINUTE`); the rest of that minute are refused without a row. Without this, one account could grow the audit table without limit, since the gateway limit is per address. The `format` and `lang` in a row are the validated values, so a row never carries unvalidated caller text beyond the ticket (cut to 40 characters).

## 4. Limits and time zone

- **Size.** The export reads a whole case and renders it in the request worker, so each source (status history, timeline, attachments, feedback, notification log, reassignments) is capped at 1,000 rows and the file at 15 MB. A case past either is refused with `400 VALIDATION_ERROR` and an `export_failed` audit row (`ExportTooLarge`). It is not cut short: a form that looks complete and is not is worse than none. The gateway tier (60 a minute) bounds how often.
- **PDF engine start-up.** Importing WeasyPrint takes about four to five seconds per worker process on an idle machine (more under load), so the first export a worker serves is slow and every export after it on that worker is fast (about 0.4 s here on an idle machine). `services/pdf_engine.py` loads the library lazily, on that first export: a pod boots lean, and the workers that serve intake, login and status checks never load WeasyPrint, Pango or the fonts. There is deliberately no warm-up at worker start. It would run on the first request a worker serves, which in a cluster is usually a health probe, so every worker would load the library at once at pod start, on CPU a container may be throttling, whether or not it ever exports. Nothing runs at import time, so a migrate, a console or a worker that never exports never loads it either. What is kept between requests is the library and one font configuration per thread (Pango's font map is not shared between threads); no ticket or user data is cached. If the server lacks Pango or the fonts, the export fails through its normal path (`export_failed` audit row).
- **What the library costs a web worker** (measured on the dev bench, one process playing a worker; a worker pays this once, on its first export): about 36 MB of resident memory and about 1.6 s of CPU for the import and first render; the first export render adds about 11 MB more; memory then levels off at roughly 245 to 255 MB for the whole process after about 30 renders and does not keep growing (60 renders: 245 MB with no warm-up). A render is CPU-bound on one core for its whole length (about 0.35 s on an idle machine, 0.6 to 1 s when the machine is busy; mostly font subsetting). Each worker that serves an export keeps the library afterwards, so if that becomes a memory concern the answer is a dedicated export deployment or route, not warming. Watch worker memory and gateway timeouts as export use grows.
- **Time zone.** Every date and time on the form is in the site's time zone, which is how Frappe stores them. The footer, and the `Export` rows of the CSV, name it with its offset (`Time Zone: Africa/Addis_Ababa (UTC+03:00)`).

## 5. How the form is filled

The PDF is laid out like the Annexure: the letterhead (the federation, then the region and the filing office, named from the case's administrative area), the title, a shaded four-column reference block, and twelve numbered sections of `Label: value` lines. A field with nothing to show prints an em dash (—), so a reader can tell "none" from a gap; only the Signature and Official Stamp lines stay blank, to be completed by hand. Checklists, their "Other" lines and the tables are not given dashes, and the CSV keeps empty values empty. The form's own wording ("Following review and verification, the responsible office determined that:") is printed as it is. The history tables sit under the section they belong to, and the whole timeline follows on its own page. The data model has no record of its own for an investigation, a decision or an appeal, so those are read from what the workflow leaves behind. A field the system never captures is left empty; nothing stands in for it.

| Annexure                            | Taken from                                                                                                                                                                                                                                                                            |

| Receiving Office                    | `assigned_dept`. Document Type is printed as "Grievance Record"                                                                                                                                                                                                                       |

Every table is ordered by time, oldest first. A stage that has not happened says so in a note ("No decision has been recorded.") and its table is left out.

## 6. Not covered

- **Wording without Amharic yet** stays in English (§7). That includes the footer's Time Zone label.
- **Dates are Gregorian** in both languages. The Amharic form uses the Ethiopian calendar, which needs a conversion that is not built.
- **The letterhead** is built from the case's region and filing office (its woreda, or zone) and reads "<name> Administration". The sample's "City" and "Sub-City" are part of its own names and are not added.
- **Document checklist.** `Grievance Attachment.document_type` is free text with no list of values behind it, so an item is ticked only by an attachment whose document type names it (ignoring case, spacing and punctuation), and any other attachment ticks Other Supporting Documents. Until the upload form sends those six names, most files will land under Other.
- **Boxes the system cannot answer.** Correct official record, additional site verification, written clarification, no action required, Written Letter, Telephone, In Person, Satisfied and Not Satisfied are left unticked: the system holds the department's own words as the action taken, and a 1 to 5 rating has no documented line between satisfied and not. They are for whoever completes the printed form by hand.
- **Occupation.** The Annexure's sample lists Occupation under Complainant Information and `database-schema.md` gives `submitters.occupation`, but this app has no such field, so the row is printed with a dash and is never inferred from other data. Capturing it would be a new field and a change to registration; removing the row if the form no longer needs it is one line in `_complainant`. Reported here as a gap, not decided.
- **Priority.** Removed from the form for the same reason: nothing records it. Add the row back when priority is captured.
- **Decision: the PDF is not digitally signed.** The exported PDF carries no digital signature, seal or QR code, and it does not replace the signed paper form. The Signature and Official Stamp fields are blank on purpose, and the footer's plain-text "Exported By" and "Exported On" are not an integrity control, since anyone can retype them. **The only integrity control is the SHA-256 in the export's audit row (§3):** it shows that a copy is unaltered and which export produced it, not who vouches for it. Decision recorded 2026-10-28 in the review of STG-469. If this changes, signing is a new ticket: a certificate-based signature or a QR code carrying a signed payload, with legal advice on whether it is binding.
- **Existing denials.** `audit.log_denied` calls made before this change (the attachment endpoints) are not durable and are lost to the same rollback. Pass `durable=True` there to keep them.
- **Proposed closure date.** FSD Appendix D-1 requires one on every department response. The service does not store it, so it cannot appear in the form.
- **Responder name for a submitter.** FSD D-4 lets a submitter see the responder's name. The timeline API shows a submitter only the officer's role, and the export follows the API, so a submitter sees "Officer". Say if the form should name them.
- **Per-response audit fields.** FSD D-3 lists the response's IP address, prior and new status and the notification sent. The status change is in the Decisions table; the IP address is not recorded per response, so it is not exported.
- **Bulk export.** The System Design lists `POST /api/v1/reports/exports` (a queued CSV or PDF of a filtered selection, staff only). That is the reports export and is not part of this ticket.
- **PDF generation stays in the web worker.** The export is a synchronous `GET` that returns the file, which is the contract the API and its clients have. Rendering is CPU-heavy, so several people exporting PDFs at once can occupy web workers and risk timeouts on other routes; the gateway tier (60 a minute) and the size caps bound it but do not remove it. The longer-term answer is to render on a background queue (`frappe.enqueue(..., queue="long")`) or a document service, but that changes the contract (a `202` with a job id, status polling and a download route), so it is a separate ticket. The audit rule would carry over unchanged: no file is handed over before its row is committed, and that write cannot itself be queued.

## 7. Language

`lang=am` prints the form's own wording in Amharic: the letterhead, the title, the reference block, the twelve section titles, the field labels, the checklists and the wording printed on the paper form. What people wrote on the case (the description, the responses, the notes) is never translated.

The wording is in `oan_grievance_service/translations/am.csv`, which Frappe loads like any app translation, and every label already goes through `_()`. Each entry is the Annexure's own Amharic, copied from the document; the one composed entry is `{0} አስተዳደር` ("{0} Administration"), built from the Annexure's word for administration around the region or office name. An admin can override any entry from the desk with a `Translation` record for `am`.

- **The English text is the key.** Rewording an English label in the code drops its Amharic until `am.csv` is changed to match. The same word with two meanings takes a context (`Telephone` for the phone number, `Telephone` in the Communication Method boxes).
- **Wording with no Amharic stays English** instead of failing: for example Submitter Type, Email, the table column headings, and the notes such as "No decision has been recorded." The Annexure has no Amharic for them. Add rows to `am.csv` when a translator supplies them.
- **Area names** are printed as they are stored, so a region and office stored in English appear in English next to the Amharic word for administration.
- **The PDF needs an Ethiopic font on the server.** Install Noto Sans Ethiopic (SIL Open Font License), for example from the `fonts-noto-core` package, or Abyssinica SIL. Without one, every Amharic character in the PDF, translated labels and the complainant's own words alike, prints as an empty box. The font list in the PDF style is Liberation Sans, Arial, Noto Sans Ethiopic, Abyssinica SIL, Nyala. The CSV does not depend on a font.
